# Unit v0.2.4 addendum (D40) — Implementation plan: BASTA special probe

> **Drafted 2026-09-17.** Four self-contained phases on the D40
> design (`20_DESIGN/units/v0.2.4-basta-addendum.md`; strategy
> `10_STRATEGY/v0.2.4.md` §"Addendum — BASTA special probe").
> ENG review SMALL CHANGE folded same day (decisions 1A / 2C / 3A /
> 4B). Every phase is offline-built and offline-tested; PHASE02/03
> touch the real network only under `GO=1 make basta-probe` (the
> polite fetcher, robots + crawl-delay honored, no browser
> impersonation). Build order: PHASE01 → 02 → 03 → 04; each phase's
> test suite stays green.

## PHASE01 — Pin: the anonymous search route behind /sok (offline-developable)

**Goal:** make the client shell's real search route discoverable by
code, or record honest unavailability — the core reconnaissance
deliverable.

- Constants db1/db2 in `basta_probe.py`.
- Fetch `/sok` (1 GET), extract `assets/ui/*` bundle URLs; fetch the
  bundle chain (≤ db2 GETs); locate the search route the client
  calls (   (candidate names: `apiUrl`-relative path, `vppHost` route, or a
  thin `/api/*` proxy on the same origin as the keyfigures route).
  Search heuristic: grep the bundle text for candidate literals
  (`search`, `sok`, `articles`, `apiUrl`/`vppHost` suffix patterns)
  — never execute JS.
- Structure record: field names from one real or fixture-shaped
  JSON body (the db6 field names are relaxed to match reality).
- **Real-run gate:** `GO=1 make basta-probe` → findings rows
  (`basta_special_unavailable` with `pin-found` in notes when it
  pins, else the honest why-not) + the /sok HTML archived (raw
  store).
- Fixture tests before the real run (12+ new tests target).
- Exit conditions: pin-found → PHASE02; pin-not-found →
  TODO-manual-browser fallback (documented, still ships PHASE04
  summary with the unavailable-mech finding).

## PHASE02 — Shape + counts (GO=1 network stage, tiny)

**Goal:** exact public pool numbers + the payload shape under the
pinned route.

- `GET /api/keyfigures/1` and `/2` (exact article + company counts)
  → finding `basta_special_records` with URL + access date.
- Pinned-route probe with `pageSize=3` + paint filter (db5)
  → structure record: header/name list, identity columns, category
  values, auth-route verdict (401 → db7 wording in an
  `unavailable-mech` finding).
- Archive every successful JSON body to the raw store.

## PHASE03 — Seeded draw + CSV (GO=1, the deliverable)

**Goal:** the 100-article random sample as CSV.

- Paint filter (db5): if pinned reliably → in-scope pool build
  (paginated, ≤ db3 threshold); else → fallback method (random-page
  or all-articles + category column) with the method recorded.
- `random.Random(seed)` draw over the canonical distinct-article
  pool (dedupe on the identity tuple: manufacturer + article number
  + basta_id); shortfall recorded if pool < n.
- CSV via the shared writer (`_write_sample_csv`): verbatim BASTA
  fields + `PROVENANCE_COLUMNS` + method column.
- Finding `basta_special_rows` (notes carry seed, method, pool size,
  shortfall); exit 0.
- offline: full draw/migration/exit-code test matrix first;
  real run only after the suite is green.

## PHASE04 — Records, AS-33 refresh, summary, report

**Goal:** everything the run produced is visible to a reviewer
without reading the CSV.

- Refresh the AS-33 register note (195,390 articles; 1,925
  companies; probe outcome; the standing ">200,000 claimed" line is
  superseded by the exact public figure).
- Register `data_sources.csv` update **only if** the draw delivered
  (de5 gate: bulk + identity tuple + in-scope filter derivable);
  otherwise the de6 heading in DATA_SOURCE.md stays as is (the
  why-not is in the strategy + summary).
- Generated artifacts: per-run
  `basta-special.<ts>.{md,csv}` + "latest" copies rendered offline
  from the DB (`--rebuild-summary`), appended snapshot in
  `docs/report/` (publish-history policy).
- Non-blocking outcome text for `report-0.2.4.md` addendum + the
  read-README/summary tie-in (README unchanged until user says
  otherwise).
- Retire nothing: existing v0.2.4 files/logs untouched.

## Completion conditions

- All five phases have findable records in the DB with provenance
  (URL + access date + doc hash) and the audit stays clean.
- The offline test suite count grows ≥ 12 (still 100% offline).
- The D40 strategy text stays as written unless execution produces a
  corrected fact (then an `_updated` line, never silent).
- Build stops on user GO only (never auto-aborts silently); every
  network-stage exit is either 0 (expected unavailable/delivered) or
  2 (genuine failure) — no silent path.

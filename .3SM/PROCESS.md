# lead_HS — 3SM Process (per-project law)

Generated by `3sm-setup` from the canonical pair
(`~/.config/opencode/3SM_structure.md`, `3SM_process.md`). This file is the
operative process law for this project: it restates the process compactly,
carries the loop/gate map, and adds ONLY project exceptions (bottom section).
Canonical stays the source of truth; `3sm-housekeeping` flags drift.

# Reading order (every agent, every session)

1. This file + your role file (`PROCESS_STRATEGY.md`, `PROCESS_DESIGN.md`,
   or `PROCESS_IMPLEMENTATION.md`).
2. `.3SM/PROJECT.md` — project facts: commands, gates, laws, defects.
3. `.3SM/plan/MASTER.md` — what is active.
4. Startup reconcile (role file): recent git log vs ledgers; drift → propose
   correction; user approves before any change.

# Roles

- **STRATEGY** — `strategy` agent: unit WHAT/WHY, U-doc, strategy T-docs.
- **PLANNING** — plan mode: design and implementation planning.
- **EXECUTION** — build mode: executes runs and lifecycle git actions.

The user declares the role per session; if unsaid, ASK before producing
output. Cross-role leakage is a serious error. One active unit at a time —
parallel units are forbidden (exceptions live in this file's exceptions
section, never improvised).

# States

    Unit stage:     STRATEGY | DESIGN | IMPLEMENTATION | COMPLETE
    Doc lifecycle:  LIVE | FROZEN | ARCHIVED      (independent of stage)
    Run state:      PLANNED | IN PROGRESS | DELIVERED | CLOSED | ABANDONED

# Working rhythm (conversation-first, non-linear)

Stages are territories, not a pipeline. The default motion is discussion;
skills are consolidation checkpoints invoked mid-discussion:

    strategy discussions → 3sm-strategy-unit → discussions → U-doc updates → …
    design discussions → 3sm-design-master → 3sm-plan-run (impl docs) →
    3sm-design-unit → discussions …
    3sm-plan-run → engineering discussions → 3sm-plan-run
    build run → user test & review → design discussions → … (loop freely)

Anti-pattern: running setup → init → strategy → design → plan → build as a
linear chain without returning to discussion. After every skill, return to
the conversation; user test/review may loop back at any time.

# Unit lifecycle

    init (user/build branch, 3sm-strategy-unit)
      → STRATEGY    U-doc converges; freeze gate (user)
      → DESIGN      unit dir: MASTER, T-docs, RUNS.md; runs-ready gate (user)
      → IMPLEMENTATION   run loop r01..rN; FINAL planned
      → FINAL       final gate (user) → merge → branch delete
      → COMPLETE    archive at next housekeeping

# Run sizing

One run = one user-testable increment (feature slice, coherent fix set).
Needs more than ~one working session or ~8 files → split. Not user-testable
→ phase inside a run. Runs may be reshaped at run-planning time if RUNS.md
records the change and reason.

# Gates

Run gate (every run): fast static checks of changed files (lint, format,
typecheck); the user reviewed the increment (manual test / review session —
the run's ONLY verification); RUNS.md row updated (status, SHA, review
outcome); no unplanned files touched. No test suite is executed and no
automated tests are authored in a regular run.

Testing economy (law): a regular run plan is a functional implementation
plan, verified by the user's manual testing. ALL automated testing —
authoring and executing: the full test suite, coverage, security scans,
evals — happens ONLY in the FINAL run (planned by `3sm-plan-final` from
PROJECT.md § Testing & security guidelines). A regular run executing or
authoring tests is a violation unless the user explicitly asks. Release
tags are lean — thorough verification happens once, at FINAL. Regular-run
gate budget: seconds to a minute, not minutes.

FINAL gate (once per unit): all runs CLOSED or deferred with recorded reason
consistent with the unit definition of done; the full test plan executed —
every FINAL test-plan input reconciled (promoted to a test, covered
elsewhere, or dropped with reason — no silent test debt); full test suite;
full lint; whole-unit diff reviewed (ship-unit pass);
ship-profile checklists executed (PROJECT.md § Ship profile); persistent
T-docs synced; U-doc and R-doc closed; merge clean.

# Naming

- Unit ids: user-chosen — version units (`v0.1.0`) or plain names
  (`importer`); no type prefixes. Dirs and branch use the id verbatim.
- Runs: zero-padded `r01…`; final run dir `FINAL/`. ALL phase plans of a
  run — completed and pending — live inside its dir; completed phases stay
  in place as the run's record. The unit M-doc tracks phase status; RUNS.md
  mirrors it. Folding finalization into the last regular run requires
  explicit user direction, recorded in RUNS.md (the full FINAL gate still
  applies).
- Topics: ≤10 top-level entries per stage (files or topic folders); folders
  group large areas, uncapped inside; consolidate when exceeded.

# Git law

- Git is the planning history: all `.3SM/` content is committed, including
  sessions. Unit planning docs live on the unit branch and merge with it.
- Working discipline (live todos + per-step commits):
  - Start every skill pass by creating a detailed todo list (the todo
    tool) mirroring the skill's checklist — one item per step, section,
    gate. Update statuses in real time; never batch-complete at the end.
    The closing skill record mirrors the todo trail.
  - Commit each step: every completed todo item, section, or doc write
    ends in its own commit before the next starts (`3SM: <skill> <step>`
    for planning passes). A pass never accumulates uncommitted steps.
- Commit-every-step: every skill invocation and every planning session ends
  committed. Stage intentional files only; never `git add -A`; never commit
  broken state at run boundaries.
- Conventions: `WIP: <what>` (during a run), `r01: <summary>` (end of run),
  `FINAL: <summary>` (pre-merge), `3SM: <event>` (lifecycle events).
- Planning agents may stage and commit `.3SM/` content only; branch creation
  happens at unit init (user/build), merge and branch-delete at ship
  (build context). Push only on explicit user instruction; local-only repos
  are first-class.
- Init gates (3sm-strategy-unit): clean tree; unit id is not an existing
  branch; id not already registered in the impl MASTER (LIVE or ARCHIVED);
  user confirmed id + theme.
- FINAL procedure (3sm-ship-unit, build context): verify FINAL gate →
  interactive rebase squashing WIPs into run commits (rebase conflict: stop,
  present, user chooses resolve or abort-to-raw-merge) → `git merge --no-ff`
  (`Merge unit <id>: <theme>`) → post-merge MASTER + LOG on base →
  `git branch -d <unit>`. Fallback per unit: merge raw history, recorded as
  a MASTER decision.
- Merge conflicts: stop; present; user decides; never auto-resolve semantic
  conflicts. Tests red at FINAL → no merge.

# Shared conventions

## Decision briefs (AskUserQuestion format)

- `D<N>` header, grounding sentence (project/branch/task), ELI10, stakes,
  `Recommendation: X because …`, completeness score or kind-note, pros/cons
  per option, `Net:` line.
- One issue per question; never batch. Question craft applies (labels,
  escape hatch, preference mapping).

## STOP cadence

Reviews proceed one issue at a time; the agent stops and waits for the
answer before continuing. No issue drives.

## Review conventions (all reviews inherit these)

**Engineering preferences** (map every recommendation to one of these):

- DRY — flag repetition aggressively, with file references.
- Well-tested is non-negotiable; rather too many tests than too few.
- "Engineered enough" — not fragile/hacky, not premature abstraction.
- More edge cases over fewer; thoughtfulness > speed.
- Explicit over clever. Minimal diff — fewest new abstractions and files.
- Observability and security are scope, not afterthoughts.
- Deployments are not atomic — plan partial states, rollbacks, flags.

Project overrides live in `PROJECT.md` § Review preferences.

**Prime directives:**

1. Zero silent failures — if a failure can happen silently, that is a
   critical defect in the plan.
2. Every error has a name — specific class, trigger, rescue, user-visible
   result, and whether it is tested. Blanket "handle errors" is a smell.
3. Data flows have shadow paths — every flow has happy + nil + empty +
   upstream-error; trace all four.
4. Interactions have edge cases — double-submit, navigate-away, stale
   state, slow connection, back button; map them.
5. Diagrams are mandatory — no non-trivial flow goes undiagrammed.
6. Everything deferred must be written down — OPEN ITEMS or it doesn't
   exist. Vague intentions are lies.
7. Optimize for the 6-month future — if the plan creates next quarter's
   nightmare, say so explicitly.
8. Permission to say "scrap it" — a fundamentally better approach is
   tabled now, not after build.

**Question craft (reviews and briefs):**

- One issue = one question; never batch (SMALL-mode batch is the only
  exception, and even there each issue keeps its own recommendation).
- Re-ground first: project, branch, task — assume the user looked away
  for 20 minutes. Explain what it DOES, not what it is called.
- `RECOMMENDATION: X because …` + one sentence tying it to a preference.
- 2–3 lettered options incl. "do nothing" where reasonable; one line per
  option: effort, risk, maintenance.
- Label issues `3A`-style (number + letter). Mark findings
  `CRITICAL GAP` / `WARNING` / `OK`.
- Escape hatch: no issues → say so and move on; obvious fix with no real
  alternatives → state what you'll do and move on. Only ask when there is
  a genuine tradeoff.
- ≤8 top issues per section; prioritize ruthlessly.

**Priority hierarchy under context pressure:**

    Step 0 (scope) > system audit > error/rescue map > test diagram >
    failure modes > recommendations > everything else.
    Never skip Step 0, the audit, the error map, or the failure modes.

**Diagram law:**

- Dual output: `flowchart` skill is the primary generator (PNG/SVG/Mermaid);
  ASCII fallback always included in planning docs — ASCII is the baseline.
- Required types when applicable: system architecture, data flow (with
  shadow paths), state machine (with invalid transitions), error flow,
  deployment/rollback sequence.
- Diagram maintenance is part of the change — stale diagrams mislead and
  are worse than none; audits flag stale diagrams even out of scope.

**OPEN ITEMS (the TODO ledger) — rich format, one per question:**

    What / Why / Pros / Cons / Context (understandable in 3 months) /
    Effort (S-M-L-XL) / Priority (P1-P3) / Depends on

    Options: A) record as OPEN ITEM (LATER)  B) skip  C) do it in this unit

A recorded open item without context is worse than none. Never silently
skip; never silently default an unanswered question — list unresolved
decisions at the end ("decisions that may bite you later").

**Retrospective check:** before reviewing, check history (git log, prior
reviews, ARCHIVED material) for previously problematic areas — be more
aggressive there; recurrence is an architectural smell.

**Completion summary:** every review ends with one compact table — mode,
findings per section, outputs written, critical gaps, unresolved decisions.

**Required review outputs:**

- NOT-in-scope list (considered and deferred, one-line rationale each)
- What-already-exists (existing code/flows that solve sub-problems; reuse
  or rebuild-and-why)
- Failure-mode registry (`codepath | failure | rescued? | tested? |
  user sees? | logged?` — any silent+untested+unhandled row = CRITICAL GAP)
- Error & rescue registry (exception classes, rescue actions, user impact)
- Test diagram (every new UX flow, data flow, codepath, job, integration,
  error path; per item: test type, exists?, happy/failure/edge specs)
- Dream-state delta (where this leaves us vs the ideal end state)
- Completion summary + unresolved-decisions list

## Skill records (the checklist trail)

Every skill invocation ends with a record in the doc it operated on, so any
future agent sees when each skill ran on which content, with which findings —
and skips what is already covered instead of repeating it.

Format (append-only — never rewrite, never prune):

    ### <skill> <mode/verdict> — YYYY-MM-DD
    scope: <docs/content the pass covered>
    checklist:
    - [x] <item> — OK / <finding + label>
    - [ ] <item> — SKIPPED: <reason> | FAIL: <finding>
    findings: CRITICAL GAP <n> · WARNING <n> · unresolved <n>
    carries: <authorized skips / handoffs for downstream skills>
    valid-until: <condition that invalidates this record>
    commit: <sha>

Location map:

    skill               record lives in
    3sm-strategy-unit   U-doc (plan/STRATEGY/<unit>.md)
    3sm-design-master   plan/DESIGN/MASTER.md
    3sm-design-unit     plan/DESIGN/<unit>/MASTER.md
    3sm-plan-run        RUNS.md (the run's section)
    3sm-plan-final      RUNS.md (FINAL section)
    3sm-ship-unit       RUNS.md FINAL section + plan/LOG.md
    3sm-setup           plan/MASTER.md
    3sm-housekeeping    plan/MASTER.md

Rules:

- Read prior records before working: skip items a record marks OK and items
  its `carries` authorizes; re-run anything whose `valid-until` fired
  (upstream re-freeze, re-plan, template upgrade, PROJECT.md change).
- A record without a commit is not a record (commit-every-step).
- Records are evidence, not authority — they never flip lifecycle state.
- Housekeeping archives records with their docs; it never edits them.

## Binding markers

Only content marked `DECISION` / `AUTHORITATIVE` binds. Grandfathered
equivalents ("settled", "locked", "Invariants") bind as DECISIONs. Nothing
under `_archive/` binds. Drift rule: a unit's own docs win over topic docs
for that unit's scope.

## Session records (S-rec)

`sessions/<date>-<unit>-<n>.md` — short: role, task, outcome, state changes.
Committed; housekeeping prunes per retention.

## Ordinary writes never imply advancement

Every gate is an explicit user action. Document edits never flip lifecycle.

# Project exceptions (amend here — nowhere else)

Process deviations from the canonical law live in this section only.
Project facts and conventions (commands, ship laws, defects) live in
`PROJECT.md`, not here.

- **Legacy v1 planning tree (migration 2026-09-18):** the planning
  history 2026-08-31 → 2026-09-17 lives in `docs/plan/3SM/` (v1
  layout: `10_STRATEGY/`, `20_DESIGN/`, `30_IMPLEMENTATION/`). It is a
  read-only historical reference — never edited, never the live tree.
  All live planning happens under `.3SM/`. Distilled unit history:
  `plan/STRATEGY/DEV_HISTORY.md`. Archiving or removing the legacy
  tree is a user decision at housekeeping, never an agent default.
- **Pre-v2 units built under v1 rules:** units v0.1.1 … v0.2.4 were
  built before this law existed (phase plans in `30_IMPLEMENTATION/`
  per unit, offline test suites per build). Their records stay in the
  legacy tree; their distilled history is `plan/STRATEGY/DEV_HISTORY.md`.
  The v2 run grammar (`r##/PHASE##.md`, FINAL gate, testing economy)
  applies from the first post-migration unit onward.
